# Постоянные правила работы

## Навигация и область изменений

- Сначала прочитай этот файл и `PROJECT_MAP.md`, затем открой минимальный набор релевантных исходников. Расширяй поиск по реальным зависимостям.
- Актуальный исходный код — source of truth; карта — навигационный индекс. При противоречии проверь код и точечно исправь карту.
- Не повторяй широкий анализ без необходимости: допустимые причины — отсутствующая/устаревшая карта, крупная перестройка, задача на весь проект или недостаточность локального поиска.
- Не анализируй зависимости, сборки, кэши, логи и бинарные артефакты: `node_modules`, `.next`, `venv`, `__pycache__`, `dist`, `build`, `coverage`, `.git` и аналоги.
- Делай минимально необходимое изменение, соблюдай стиль, переиспользуй существующие решения. Не добавляй архитектуру или зависимости без реальной пользы. Перед значимой зависимостью сообщи обоснование и влияние.
- Для bugfix установи причину, проверь реальные связанные места, validation, permissions и error handling. Не оставляй debug-код.
- Обновляй только затронутые разделы карты после изменений архитектуры, API/data flow, ролей, моделей, важных модулей и интеграций. Обычный bugfix не требует переписывать карту.
- Этот файл стабилен: меняй только при изменении постоянных правил; не веди здесь журнал задач. Не описывай запланированное как реализованное.

## Пользовательская работа и восстановление

- До существенных изменений проверь Git status, branch, HEAD и незакоммиченные изменения. Зафиксируй исходный HEAD в отчёте.
- Если Git отсутствует, не инициализируй его автоматически и не создавай commit. Если пользователь явно попросил создать/подключить Git-репозиторий, можно выполнить только запрошенные локальные и remote операции.
- Все существующие изменения считай важной пользовательской работой. Не удаляй, не откатывай и не перезаписывай их без необходимости. Если есть реальный риск потери при пересечении файлов — остановись и спроси.
- Не выполняй автоматически stash, destructive Git operations, `reset --hard`, `clean`, force push. Для разрушительных операций требуется явное разрешение.
- Не создавай физические копии или архивы всего проекта, даже временные; не дублируй зависимости, uploads, базы или сборки ради backup.
- Для обычных изменений используй существующий HEAD + diff + проверки. Не создавай backup commit/branch для каждой задачи; локальная branch допустима при необходимости для крупного рискованного изменения.

## Границы доступа

- Технический доступ не означает разрешение. По умолчанию разрешены локальное чтение, локальные правки по задаче, безопасные локальные проверки и Git inspection.
- Без явного разрешения на конкретную операцию запрещены push, remote write/merge/branches/releases, изменения CI/CD, deploy, SSH, staging/production access, production DB (включая SELECT), реальные production data и внешние побочные действия.
- Обычное «исправь/проверь/сделай» разрешает локальную работу, но не production, remote или реальные вызовы внешних сервисов. Разрешение ограничено указанной операцией и текущей задачей.
- Если окружение неизвестно, считай его production до выяснения. Перед потенциально опасным действием остановись: объясни где/зачем, операцию, чтение/изменения, риски, rollback, необходимость backup и безопасную альтернативу; дождись разрешения.
- Не запускай реальные email/SMS/мессенджеры, платежи, webhooks, cloud/storage/Google/AI API ради проверки. Supabase здесь внешний сервис: запуск UI/API может обратиться к нему.
- Не подключайся к production DB, не запускай migrations/seed/дumps/import/export/restore автоматически. Backup БД требует отдельной оценки и разрешения, если нужен дополнительный доступ; Git не является backup БД.
- Для разработки используй schemas, fixtures, mocks и подтверждённую local/test DB. Если нужны production data, объясни причину, невозможность локального решения и минимальный доступ, затем дождись разрешения.
- Предпочитай config code и имена переменных из example-файлов. Не открывай реальные `.env`, `CREDENTIALS.txt` и секреты без необходимости и разрешения. Никогда не записывай secrets/credentials/реальные данные в код, Git, документацию, ответы или логи. Случайно найденное не воспроизводи.

## Проверки и отчёт

- До запуска команды проверь, что она не обращается к production или внешнему сервису. Не импортируй приложение и не запускай скрипты настройки БД ради проверки документации.
- Выполняй подходящие безопасные локальные проверки; для локальной правки выбирай точечные, для критической общей части расширяй область. Проверь diff на случайные изменения, secrets и лишние зависимости.
- После существенной задачи сообщи: FILES CHANGED, ORIGINAL HEAD, RESTORE METHOD, TESTS, PROJECT_MAP UPDATED, AGENTS.md UPDATED, GIT COMMIT CREATED, GIT PUSH, PHYSICAL PROJECT BACKUP CREATED, PRODUCTION ACCESSED, PRODUCTION DATABASE ACCESSED, PRODUCTION DATA ACCESSED, DEPLOYED, EXTERNAL SIDE EFFECTS.
