# Локальный запуск и подготовка VPS

Приложение использует отдельные контейнеры PostgreSQL, PostgREST, FastAPI и Next.js. PostgREST нужен только как приватный REST-адаптер к PostgreSQL внутри Docker-сети; к облачной платформе Supabase приложение не подключается. Аудио хранится в постоянном Docker volume. База и PostgREST не публикуются на внешние порты.

## Запуск в один клик на Windows

1. Установите Docker Desktop и дождитесь запуска.
2. Дважды щёлкните `Start-AISezim.cmd` в корне проекта.
3. Откройте `http://localhost:3000`.

Запускатель создаёт `.env` со случайными секретами при первом запуске, проверяет доступность Docker и конфигурацию Compose, а затем собирает и запускает production-образы. Первый запуск требует интернета для загрузки образов. Остановка без удаления данных: `docker compose -f docker-compose.yml -f docker-compose.desktop.yml down`. Не добавляйте `-v`, если нужно сохранить базу и аудиофайлы.

## VPS с доменом и HTTPS

1. Установите Docker Engine и Compose plugin на Ubuntu VPS, откройте входящие TCP 80/443 (и UDP 443 для HTTP/3). Не открывайте PostgreSQL 5432 и PostgREST 3001.
2. Разместите рабочую копию проекта на VPS разрешённым способом. Укажите A/AAAA-запись домена на IP сервера.
3. Создайте `.env` из `.env.example`, установите случайные секреты и свой домен. В Linux для каждого секрета можно создать значение командой `openssl rand -hex 32`. Не используйте одинаковые секреты и не загружайте `.env` в Git.
4. Выполните `bash ops/start-vps.sh`. Скрипт проверит Docker и конфигурацию Compose, соберёт образы, дождётся healthcheck приложения и покажет состояние контейнеров. Альтернативно запустите `docker compose --profile vps up --build -d --wait --wait-timeout 180`.
5. Проверьте `docker compose ps`, `docker compose logs --tail=100 backend frontend caddy` и страницу `https://<ваш-домен>/`.

Caddy завершит HTTPS и проксирует только веб-приложение. FastAPI опубликован на loopback сервера для диагностики и недоступен напрямую из интернета; вызовы интерфейса проходят через Next.js proxy.

## Данные и резервное копирование

Новая схема создаётся только при первом запуске PostgreSQL с пустым volume из `backend/migrations/standalone_init.sql`. Обычный `up --build` сохраняет существующий volume и не перезапускает инициализацию. SQL-файлы в `backend/migrations/` не применяются автоматически: для уже созданной базы отдельно проверьте и примените нужные миграции. В частности, `07_intake_creator_retention.sql` позволяет удалять аккаунты сотрудников, сохраняя историю приёмов и подписей. Сначала проверяйте миграции на локальной копии. Резервное копирование `postgres_data` и `media_data` должно выполняться отдельно; Git не содержит пользовательские записи и аудио.

Существующие данные облачной базы в этот локальный контур не копируются автоматически. Перенос данных требует отдельного разрешения на чтение исходной базы, согласования состава персональных данных и проверенного локального импорта. До такого переноса новый контур начинается с пустой базы и подготовленных демонстрационных примеров интерфейса.

## Требования к окружению

- Локальная разработка: Docker Desktop с Compose plugin.
- VPS: Ubuntu LTS, Docker Engine/Compose plugin, публичный домен с DNS и разрешённые TCP 80/443.
- Образы закреплены по основным веткам PostgreSQL 16, PostgREST 16.3, Caddy 2.10 и Node.js 22; точные обновления проверяйте перед обслуживанием сервера.
