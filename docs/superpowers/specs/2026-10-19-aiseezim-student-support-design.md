# AISezim: поддержка учеников, работа психологов и дорожная карта

Дата: 2026-10-19  
Статус: дизайн согласован в чате; следующая стадия — реализационный план  
Исходный commit: `a18120ed2a75ad8af6607919d8ddc29505145cf9`

## Цель

Подготовить AISezim как self-hosted платформу поддержки школьников: ученик может безопасно получить первую помощь от бота или обратиться к живому психологу, а психолог — восстановить всю историю общения и вести дальнейшую работу. Поддерживаются два маршрута: психолог русскоязычных классов и психолог казахскоязычных классов. Поверх надёжной основы продукт развивается как связанный цикл «обратная связь → поддержка → сопровождение → оценка результата».

Система работает без Supabase на PostgreSQL, PostgREST, FastAPI и Next.js. Локальный старт и VPS-развёртывание — отдельные проверяемые конфигурации. Этот дизайн не разрешает подключение к VPS, production-данным, push или deploy.

## Подтверждённое понимание требований

- Ученик может открыть анонимный чат; выбранный язык чата определяет психолога для анонимной сессии.
- У вошедшего ученика психолог определяется языком класса. Если язык класса не настроен, интерфейс явно просит выбрать язык чата и использует его как запасной вариант.
- Психологов два, с отдельными учётными записями и назначением ru/kk.
- Когда соответствующий психолог онлайн, новые сообщения появляются в его очереди; бот не должен конкурировать с ответом психолога.
- Когда психолог офлайн, бот отвечает по текущим правилам и может предложить обращение к специалисту. Просьба ученика создаёт обращение с предшествующей перепиской.
- Фразы о возможном самоповреждении, суициде или непосредственной угрозе человеку поднимают срочный сигнал: бот отправляет заранее проверенный поддерживающий ответ, а психолог получает обращение и полную хронологию независимо от присутствия.
- Психологу сохраняются все сообщения и события диалога. История отображается хронологически, доступна после закрытия обращения, ищется по времени и другим атрибутам и позволяет продолжить работу.
- Учётные записи учеников сначала создаёт администратор. Назначение кураторов и право кураторов создавать аккаунты остаются отдельным этапом после определения школьной политики.
- Пользователь в конце сам проверяет и принимает результат; реализация идёт локально и по этапам.

## Текущее состояние проекта

Исходники и `PROJECT_MAP.md` описывают Next.js/React интерфейс, FastAPI API и self-hosted PostgreSQL/PostgREST. В проекте уже присутствуют ученические методики, дневник настроения, правила/FAQ-бот на русском и казахском, анонимный и аккаунтный чат, кабинет психолога, записи на консультацию, Q&A, аудио, самопомощь, административная часть, отчёты PDF и кабинет учителя.

Критические пробелы, связанные с этим дизайном:

- Психологическая очередь общая, назначения по языку и двух отдельных очередей нет.
- Присутствие психолога и переключение bot/human отсутствуют.
- История сообщения сохраняется, но ошибки части операций записи могут быть подавлены; API может подтвердить неуспешную запись.
- Психологический интерфейс не даёт полноценного архива диалогов с фильтром по датам и поиском.
- События риска логируются, но внешние уведомления не настроены. Для первого этапа достаточно надёжной очереди, badge/unread и видимого счётчика; внешние каналы отдельно подключаются только при необходимости.
- В модели нет нормализованного языка класса. Учительский академический поток в основном демонстрационный, отдельной роли/назначения куратора и родителя нет.
- Часть текущих функций следует проверить в полном локальном сценарии; документация и бейджи production-ready сами по себе не подтверждают работоспособность.

Новая схема для Compose живёт в `backend/migrations/standalone_init.sql`; дополнительные миграции не применяются к существующему volume автоматически. Реальную базу не меняют до отдельного preflight и явного разрешения.

## Рассмотренные архитектурные пути

1. **REST + polling, рекомендуемый.** Использовать текущие API и Postgres, добавить присутствие, назначения, состояние диалога, архив и поиск. Интерфейсы обновляются текущими периодическими запросами. Минимум новых зависимостей и операций для self-hosted VPS.
2. **WebSocket и отдельный presence/message broker.** Улучшает мгновенность, но добавляет инфраструктуру, мониторинг и эксплуатационные точки отказа. Для двух специалистов и текущей платформы не оправдано на старте.
3. **Бот отвечает всегда, психолог лишь читает эскалации.** Проще, но противоречит выбранному пользователем сценарию живого ответа, поэтому не выбирается.

## Архитектурный дизайн

### 1. Язык и назначение

- Для аккаунтного ученика resolver читает `instruction_language` из записи класса; допустимые значения — `ru`, `kk`. Поскольку текущая схема хранит `class_id` строкой, первая реализация добавляет нормализованный справочник `school_classes` (`class_id`, `display_name`, `instruction_language`) и связывает его с существующим `users.class_id`.
- Для гостя resolver использует выбранный язык чата.
- Если назначение класса отсутствует/невалидно, API не угадывает: просит выбрать `ru` или `kk`, сохраняет источник языка (`class` или `chat`) в диалоге.
- Администратор связывает ровно одну активную учётную запись психолога с каждым языком. Отсутствующая настройка должна давать понятное состояние «специалист пока не назначен» и не терять обращение.
- На первом этапе аккаунты психологов создаются администратором. Права куратора не добавляются без уточнения его функций и границ доступа.

### 2. Диалог и режимы ответа

Состояния обращения: `BOT_ACTIVE`, `WAITING_PSYCHOLOGIST`, `HUMAN_ACTIVE`, `CLOSED`. Режим ответа (`bot` или `human`) определяется отдельно для каждого нового сообщения по присутствию назначенного психолога; он не уничтожает состояние обращения. События смены состояния, назначения, получения, ответа и закрытия фиксируются отдельной временной записью.

- При отправке каждого сообщения backend выбирает назначенного психолога по сохранённому языку и проверяет его heartbeat.
- Если психолог онлайн, ученическое сообщение сохраняется и появляется в его очереди; бот не создаёт ответ поверх ожидаемого ответа человека.
- Если психолог офлайн, бот отвечает только правилами и FAQ даже в уже эскалированном диалоге; существующие назначение и очередь остаются, психолог позже увидит все сообщения. Неуверенное совпадение не выдумывает психологический совет: бот предлагает консультацию или безопасный ресурс.
- Явный запрос психолога создаёт/оставляет обращение в `WAITING_PSYCHOLOGIST`; режим ответа при этом всё равно зависит от heartbeat. Ученик видит, что обращение сохранено и ожидает специалиста.
- При сигнале риска бот использует проверенный статический текст, регистрирует срочный сигнал и ставит диалог в очередь вне зависимости от online. Онлайн-статус не трактуется как гарантия экстренного реагирования и не заменяет утверждённый школой кризисный порядок.
- После принятия обращения психологом диалог становится `HUMAN_ACTIVE`. Если специалист онлайн — отвечает он; если heartbeat протух — бот может дать только rule/FAQ fallback, не меняя назначение и не притворяясь человеком. UI показывает автора каждого ответа.
- Закрытие не удаляет ни transcript, ни события.

Присутствие — heartbeat, отправляемый открытым кабинетом психолога. Начальная настройка: heartbeat раз в 30 секунд, состояние онлайн считается устаревшим после 90 секунд без heartbeat; значения конфигурируемы. UI чата и очереди продолжает обновляться примерно каждые 4 секунды, если проектный профиль производительности подтвердит такой интервал.

### 3. Сохранение, журнал и доступ

Основное хранилище — PostgreSQL. Переписка должна быть доступна назначенному психологу, а не только владельцу guest cookie. Храним все типы сообщений, автора, timestamp, идентификатор диалога и временные события назначения/передачи/закрытия. В выдаче стабильная сортировка по `created_at`, затем `id`.

Психологический архив поддерживает (времена хранятся в UTC, интерфейс показывает их в часовом поясе школы Asia/Oral):

- фильтр интервала создания/последнего сообщения;
- фильтр языка, статуса, приоритета и назначенного специалиста;
- поиск аккаунтного ученика по разрешённым полям и гостевой сессии по псевдонимному ID;
- полнотекстовый поиск по содержимому внутри разрешённой области назначенного психолога;
- хронологию сообщений и событий, пагинацию старых записей и переход в беседу;
- сохранённые обращения после закрытия и отметки прочтения/последнего ответа.

Каждый write path проверяет результат PostgREST и возвращает клиенту явную ошибку при сбое; отправка student-message, bot reply, psychologist reply и смена статуса не должны представляться успешными, если сохранение не подтверждено. Добавление сообщения и соответствующего события/статуса выполняется атомарным SQL RPC. Клиент передаёт idempotency key, чтобы безопасно повторять запрос после сетевого таймаута. Индексы нужны по `dialog_id, created_at`, assigned psychologist + status + last_message_at, и полям фильтра архива.

Доступ по умолчанию: назначенный психолог читает диалоги своего языка; психолог не может читать другого специалиста/менять назначение через подмену ID; admin управляет аккаунтами и настройками маршрута, доступ к тексту консультации следует ограничить отдельным явно определённым правом и журналировать. Учитель не имеет доступа к тексту чата. API является источником проверки ролей — UI редирект не считается защитой.

Для анонимного ученика JWT/cookie сохраняет идентичность в том же браузере. Он может потерять доступ к гостевому чату после очистки браузерных данных; это не удаляет историю из кабинета психолога. Восстановление анонимного доступа по коду — отдельная опция следующего этапа.

История не очищается автоматически. Правило срока хранения и физического удаления устанавливает школа до production; при удалении нужны авторизация, подтверждение и запись о действии без утечки содержимого.

### 4. Кабинет психолога

Рабочая очередь разделяет новые, ожидающие, активные и закрытые обращения; заметно показывает новый ответ и срочность. При открытии обращения специалист видит всю хронологию, язык, время и историю статусов. После завершения — диалог остаётся в архиве с фильтрами и поиском. Follow-up задачи, планы помощи и служебные заметки (следующая очередь roadmap) являются отдельными структурированными сущностями, не изменяющими исходный текст разговора.

### 5. Безопасные check-in и аналитика

- Самооценка настроения остаётся добровольной и не называется диагнозом.
- Следующий шаг — короткие повторные check-in и управляемые наборы вопросов с версиями, датой действия и RU/KZ-сверкой.
- Текст опросника, scoring, пороги и кризисные формулировки проходят review школьного психолога перед выпуском; существующие методики не получают новые клинические выводы автоматически.
- Отдельно задаётся, связан ли опрос с личностью или используется только для агрегированных групповых тенденций. UI должен объяснить ученику, кто увидит ответ.
- Dashboard показывает тренд, число ответов и факт выполненных follow-up. Для малой группы скрывает результаты до согласованного порога; порог задаётся школьной политикой.

### 6. UX-логика для ошибок и пустых состояний

- Нет психолога, база недоступна, не совпал язык, сообщение не сохранилось, очередь пуста, нет архивных результатов, сессия гостя потеряна — отдельные понятные тексты и следующий шаг.
- Неуспешная отправка остаётся в поле ввода/локальном черновике и может быть повторена без создания дубликата; для повтора используется idempotency key.
- Offline-страница не показывает данные, будто они синхронизированы с VPS.
- Клиентская polling-подписка останавливается или замедляется при скрытой вкладке и аккуратно восстанавливается при возвращении.

## Дорожная карта развития

Этапы упорядочены по зависимости; каждый закрывается проверяемым результатом.

### Этап 0 — Надёжность и запусковой фундамент

1. Инвентаризация пользовательских изменений, API и схемы; зафиксировать исходные проверки.
2. Исправить корректное сообщение ошибок, фиксацию транзакций, повтор/дедупликацию и проверки ролей.
3. Добавить язык класса, связь языка с психологом и heartbeat.
4. Добавить статусы bot/human, срочную очередь, полную историю и архив с фильтрами по датам и поиском.
5. Развести local-only режим и сетевые режимы, убрать вводящие в заблуждение сообщения локального запуска из продукта.
6. Проверить Windows one-click и production Compose локально, PostgreSQL volumes, healthchecks, секреты и восстановление после перезапуска. VPS остаётся ручной внешней операцией.

**Критерий выхода:** сценарии guest и account RU/KK проходят end-to-end на тестовой БД; психолог видит все сообщения в порядке времени; БД недоступна — UI не заявляет успех; посторонний психолог не открывает диалог; повторное открытие Compose сохраняет историю.

### Этап 1 — Работа психолога по обращениям

Очередь/архив; поиск по дате, классу/ученику или гостевому ID и тексту; назначение; приоритет; просмотр статусов и полной истории; отдельная внутренняя заметка; follow-up дата и итог обращения; кабинет показывает новые ответы и пропущенные сроки.

**Критерий выхода:** психолог может найти старое обращение, прочитать диалог от начала, оставить внутренний follow-up и завершить/возобновить работу без потери событий.

### Этап 2 — Ученические аккаунты и школьная структура

Управление классами и языком класса; массовое создание/импорт учётных записей через однозначный безопасный формат; начальный оператор — admin; позже отдельное решение о кураторе и его scope. Повторный вход синхронизирует профиль, чат и разрешённые данные.

**Критерий выхода:** ученик после смены устройства видит свою историю; язык класса не редактируется учеником; куратор не получает психологические записи без специально назначенного права.

### Этап 3 — Проверенные опросы и короткие check-in

Вопросники с версией, языком, периодом действия и источником; плановые/разовые короткие check-in; явный анонимный или идентифицированный режим; просьба о помощи ведёт в защищённую очередь; пользователь видит, кто увидит ответ. RU/KZ parity checks; валидация scoring и полного покрытия вопросов.

**Критерий выхода:** версия и язык ответов доступны в отчёте; смена версии не переоценивает старые результаты; низкая выборка не показывается как статистический вывод.

### Этап 4 — Библиотека поддержки и завершённый follow-up

Материалы самопомощи группируются по понятной теме и языку; bot/operator ссылается на конкретный проверенный материал; ученик может отметить полезность; психолог планирует повторный контакт и фиксирует результат отдельно от диагноза. Персональный дневник по умолчанию видит только ученик, обмен с психологом явный.

**Критерий выхода:** путь от рекомендации материала до запроса специалиста и отметки результата сохраняет контекст и прозрачен для ученика.

### Этап 5 — Агрегированная аналитика и школьный цикл улучшения

Графики динамики по времени и методикам; количество завершённых и незавершённых check-in; группы/классы только при достаточном количестве ответов; темы помощи без раскрытия текстов групповой аудитории; отчёты PDF/экспорт по разрешённым полям; цели и повторная оценка мер поддержки.

**Критерий выхода:** директор/администратор видит агрегаты без transcript, психолог — индивидуальную область полномочий, данные малых групп скрыты.

### Этап 6 — Проверяемые интеллектуальные функции (опционально)

Только после надёжных данных и review: локальная классификация тем, подсказка специалисту со ссылками на фрагменты исходного диалога, черновик ответа/ресурса с ручным подтверждением. Автоматическая диагностика, автономное психотерапевтическое решение, автоматическая смена риска и автономная кризисная рекомендация не входят в целевой продукт. Любую LLM-модель надо отдельно оценить на RU/KZ, приватности и требованиях оборудования; внешний API не используется по умолчанию.

**Критерий выхода:** любая подсказка помечена как предложение, психолог видит источник/фрагмент и подтверждает действие; при недоступности функции обычный безопасный поток продолжает работать.

## Проверки и принятие

Проверки локальные, безопасные и используют тестовые аккаунты и данные:

- unit tests для языка, назначения, состояния, очереди, risk phrases, ошибки записи и дедупликации;
- API tests для owner/role/scope, чтения/записи, поиска и фильтров диапазона времени;
- end-to-end сценарии: guest RU, guest KK, account по языку класса, missing class language, псих онлайн/офлайн, handoff, bot fallback, срочное обращение, закрытие/архив, очистка guest cookie, повтор после сбоя DB;
- PostgreSQL и Compose smoke test на изолированных локальных volumes;
- frontend production build и существующие локальные browser-check скрипты, выбранные по затронутым сценариям;
- полный diff и секреты перед завершением; обновление `PROJECT_MAP.md` и точечной пользовательской документации.

В проекте уже есть 28 backend-тестов, local browser scripts и ранее проверенная frontend production build; их фактическое повторное состояние подтвердить перед завершением. Развёртывание VPS, remote Git и production DB не входят в проверки.

## Ограничения и нерешённые решения

- Правило школы по хранению/удалению переписки, consent для несовершеннолетних и раскрытию информации семье должно быть утверждено до production, где применяются реальные данные.
- Кураторское создание ученических аккаунтов не вводится, пока не заданы обязанности и границы доступа; первая реализация — администратор.
- Автоматические уведомления за пределы кабинета (email/SMS/мессенджер) не подключены в MVP; добавление требует отдельного канала, настройки и безопасной проверки.
- Политика порога агрегирования аналитики и конкретный список опросов утверждаются специалистом/школой до выпуска.
- Профиль домена, VPS, публичный адрес и production-данные не проверяются без отдельного разрешения.
